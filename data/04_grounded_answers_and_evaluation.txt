Grounded Answers, Citations, and Evaluation

A document Q&A bot should distinguish between information found in its knowledge base and information that is not available. The language model may have broad general knowledge, but the purpose of retrieval-augmented generation is to answer questions using the selected documents. A system prompt should clearly instruct the model to use only the supplied excerpts for factual claims, acknowledge when evidence is insufficient, and avoid inventing citations. The application should independently attach source labels from the retrieved metadata.

A useful answer format is a concise response followed by a Sources section. Each source entry should include the filename and page or section, with a short excerpt that demonstrates the connection between the answer and the evidence. Showing source chunks is valuable during evaluation because it reveals whether the retrieval step returned relevant material. It also helps a user detect cases where a fluent answer does not actually follow from the source text.

Prompt instructions are only one guardrail. A model may still make unsupported claims, misunderstand the question, or combine facts incorrectly. The application should handle an empty retrieval result and should not call the model when no useful evidence is available. A relevance threshold may be added if the underlying distance metric is understood and tested. The system should not treat an embedding score as a calibrated confidence percentage. If evidence is weak or conflicting, a cautious response is better than false certainty.

Evaluation should cover more than a single successful question. Build a small test set with direct lookup questions, paraphrased questions, questions requiring evidence from different documents, and unanswerable questions. For each answerable question, record the expected source and the important facts the answer should include. For unanswerable questions, check whether the system clearly states that the knowledge base does not contain enough information. Review both answer quality and retrieval quality.

Retrieval and generation should be diagnosed separately. If the correct passage is absent from the retrieved chunks, investigate document extraction, chunking, embedding, top-k, or the index. If the correct passage is present but the final answer is inaccurate, investigate prompt instructions, context formatting, and the model response. This separation prevents developers from repeatedly changing the prompt when the real problem is retrieval. It also provides a more meaningful demonstration of engineering understanding.

Operational tests are important too. Restart the app after indexing to confirm that it loads the saved vector index. Try a missing index, an empty data directory, a malformed document, a missing API key, and a model API error. The user interface should show a useful error message without exposing secret values or a long stack trace. The command-line interface should support an interactive loop and a clear exit command, because that is a simple way to demonstrate repeated questions.

Source citations should be generated from trusted application metadata. A model can be asked to refer to sources, but it should not be allowed to fabricate a filename or page number. The application can label retrieved passages as Source 1, Source 2, and so on, then display their actual filenames and pages outside the generated text. If the model uses a source identifier in its response, the identifier can be checked against the supplied context before display. Even without sophisticated validation, separating model prose from application-generated source labels reduces citation errors.

Responsible use requires honest limitations. The system may miss a passage, misread a table, fail on scanned PDFs, or produce an imperfect summary. It is not a substitute for professional judgment in legal, medical, financial, or other high-impact settings. The README should explain the current design and its limitations rather than claim that the bot is always accurate. Clear limitations and reproducible tests are signs of engineering maturity, not weaknesses.
