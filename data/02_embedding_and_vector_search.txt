Embeddings and Vector Search

A text embedding is a fixed-length numerical representation of a piece of text. Embedding models are trained to place semantically similar text near each other in a vector space. For example, the phrases “How can I reset my password?” and “Steps to change a forgotten login credential” use different words but express a related intent. A semantic search system may retrieve the same relevant passage for both questions, whereas a simple keyword search may not.

Before embedding, a document is usually split into chunks. The embedding model processes each chunk and returns a vector. The query is embedded using the same model so the query vector can be compared with stored document vectors. Using the same embedding model for documents and queries is essential because vectors from unrelated models do not necessarily share a compatible space. The model name and relevant configuration should be recorded in project documentation so the index can be rebuilt consistently.

Vector similarity can be calculated using cosine similarity, dot product, or Euclidean distance. The best choice depends on the model and the index configuration. FAISS is a library for efficient similarity search over dense vectors. It offers several index types with different trade-offs among search speed, memory usage, and accuracy. For a small internship assignment, a flat index is easy to understand and can provide exact nearest-neighbour results. Larger collections may require approximate indexes, but those introduce more parameters and can make debugging harder.

A persistent vector index normally consists of the index data plus metadata that maps each vector position to its original chunk. Saving only the vectors is not enough: the application also needs the chunk text and source details. When the index is loaded, the metadata and index must be checked for compatible lengths. If files change, the safest beginner workflow is to rebuild the index explicitly rather than mixing old vectors with new metadata. Persisted indexes should be treated as application data and should only be loaded from trusted sources.

Batching embedding calls improves efficiency. Instead of invoking the model separately for every chunk, collect chunks into a list and encode the list in batches. The batch size should be selected based on available memory. When using a local sentence-transformer model, inference can run on CPU or a compatible GPU. CPU execution is easier to reproduce but may take longer for large collections. A model such as all-MiniLM-L6-v2 is popular for lightweight semantic search, although it may not perform equally well on every domain or language.

The top-k parameter determines how many chunks are retrieved for a query. A small k can omit evidence needed for a complete answer. A large k can add irrelevant material and consume more of the language model's context window. The appropriate value should be chosen through evaluation. For a small document collection, retrieving three to five chunks is a reasonable starting point, but this is not a universal optimum. The interface should make the value configurable so it can be tested without rewriting the pipeline.

Similarity scores should be interpreted carefully. Depending on the index, a score may be a distance where lower is better, or a similarity where higher is better. A score is not the same as a probability that the answer is correct. If a system applies a threshold, the threshold must match the scoring convention and should be tested on representative queries. A threshold that is too strict may reject valid evidence; a threshold that is too loose may allow unrelated passages through.

Useful evaluation questions include paraphrases, questions that mention a concept indirectly, questions whose answer is spread across multiple chunks, and questions that are not covered by the collection. Inspecting retrieved chunks is often the fastest way to distinguish a retrieval problem from a generation problem. If the needed evidence was not retrieved, changing the generation prompt will not solve the underlying issue. If the correct evidence was retrieved but the answer is wrong, the prompt, model, or context formatting may need attention.

A vector database is one component of a search system, not the whole system. Document quality, chunk boundaries, embedding choice, metadata correctness, query formulation, and answer generation all affect the final experience. A transparent implementation exposes enough information to inspect retrieved sources and reproduce the indexing process.
