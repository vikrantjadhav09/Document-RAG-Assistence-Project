RAG Fundamentals: Retrieval-Augmented Generation

Retrieval-Augmented Generation, commonly called RAG, is a system design pattern that connects a language model to an external collection of information. Instead of relying only on information learned during training, the system searches a selected knowledge base at question time and supplies relevant passages to the model. The model then uses those passages to prepare a response. This approach is useful when answers must reflect specific documents, internal policies, product manuals, research notes, or other information that may not be present in the model's training data.

A typical RAG pipeline has two major phases: indexing and querying. During indexing, the application loads documents, extracts text, splits the text into manageable chunks, creates vector embeddings, and stores those vectors with metadata. During querying, the application converts a user question into an embedding, searches the vector store for nearby vectors, selects the most relevant chunks, and places those chunks in a prompt for the language model. Keeping these phases separate makes the application faster and easier to operate because the document collection does not need to be reprocessed for every question.

Document chunking is important because a whole book or long report may be too large to fit into a model's context window. Chunks should be large enough to preserve meaning but small enough to retrieve specific information. Character-based chunking is easy to implement and works across many text formats. Sentence-based and section-based chunking can preserve structure more naturally, but require additional parsing. Overlap between adjacent chunks helps prevent a key sentence from being separated from its explanation. The chosen chunk size and overlap should be tested against real questions rather than selected only by convention.

Embeddings represent text as numerical vectors. A semantic embedding model places passages with related meanings near each other in vector space, allowing retrieval even when a question uses different words from the source. A vector database such as FAISS can efficiently search these vectors. The index must be stored persistently when repeated application starts should not require rebuilding it. Alongside each vector, metadata should preserve the source filename and page or section so the application can explain where an answer came from.

Retrieval quality is not guaranteed by using a vector database alone. A query can return passages that share vocabulary but do not answer the question. Useful safeguards include inspecting retrieved text, selecting a configurable top-k value, applying a relevance threshold when supported, and instructing the language model to use only the supplied context. A good system should say that the available documents do not contain an answer when evidence is missing. It should not silently fill the gap with a plausible guess.

Citations make generated answers easier to verify. At minimum, a citation should identify the filename and page number or section. The application should display the retrieved source passages as well as the citation labels, so a reviewer can check whether the response follows the evidence. A citation generated only by the language model is not sufficient; source labels should come from retrieval metadata controlled by the application.

Evaluation should include questions whose answers are present, questions that require combining information from more than one document, and questions that cannot be answered from the collection. Test the same questions after restarting the application to verify that the index is actually persistent. Also test empty files, malformed documents, missing API keys, and unavailable model services. Record known limitations, because RAG can still miss relevant passages, misunderstand tables, or produce an incorrect summary of retrieved text.

RAG is not a guarantee of truth. It is a way to make answers more grounded and auditable by connecting generation to a selected source collection. Human review remains important for high-impact decisions. A well-designed beginner project should make its workflow visible, keep indexing separate from querying, preserve source metadata, and clearly communicate uncertainty when the evidence is insufficient.
