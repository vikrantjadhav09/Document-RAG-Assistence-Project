Document Quality, Ingestion, and Metadata

Reliable document question answering begins with reliable ingestion. Files may contain repeated headers, footers, page numbers, tables, scanned images, or unusual encodings. Text extraction libraries can handle ordinary digital PDFs, but scanned PDFs may require optical character recognition. If extraction returns empty or garbled text, the application should report the problem instead of creating an empty vector index that appears to work. A document processing pipeline should count extracted characters or words and warn when a file appears to contain no usable text.

A document collection should be selected deliberately. Each document should be meaningful, substantial enough to support real questions, and appropriate to share in a public repository. A set of four or five documents can cover related but distinct subjects. The collection should include at least one PDF when the assignment requires PDF support. Before committing documents, check their licensing and remove personal or confidential information. Public documentation, open educational material, and original explanatory notes are often suitable choices.

Metadata links each chunk back to its origin. Useful fields include source filename, page number, section heading, chunk identifier, and optionally the document title. Metadata should be created during ingestion and preserved with the chunk text. A filename alone may be sufficient to identify a source file, but a page number or section makes it much easier to verify an answer. Metadata should be derived from the loader or document parser rather than invented by the language model.

PDF loaders often return one document object per page. When this is true, the page number can be stored before splitting the page text into smaller chunks. Different libraries may use zero-based or one-based page indexes. The application should normalize this convention and document it clearly. If a source does not provide page metadata, the application can use a section or a stable document-level label. It should not display a misleading page number when one is unavailable.

Chunking across page boundaries requires a design choice. Keeping pages separate makes page citations straightforward, while merging pages can preserve context across a paragraph that continues on the next page. For a beginner assignment, splitting each page independently is easier to audit. A fixed-size splitter with overlap can then divide long page text into smaller passages while preserving the page metadata. Very short fragments should be filtered or combined when appropriate so the index does not contain mostly meaningless pieces.

The ingestion process should be repeatable. An indexing script can scan a configured data directory, accept supported extensions, report the number of documents loaded, report the number of chunks created, batch-embed the chunks, and save both the vector index and metadata. It should fail with a clear message when no supported documents are found. The querying process should load the saved index and metadata, verify that they match, and stop with an actionable instruction if indexing has not yet been performed.

Version control needs attention as well. Source code, sample documents, tests, and README instructions should be committed. Secrets, local virtual environments, caches, and large temporary files should be excluded. A generated index can be excluded if it can be recreated reliably from committed documents. If a generated index is committed, the README should explain how it was built and how to rebuild it after the documents or embedding model change. A clean commit history with separate commits for meaningful steps is easier to review than one unexplained final snapshot.

Document extraction can change across library versions. Pinning compatible dependency versions and testing installation in a clean Python environment improves reproducibility. The README should list the supported Python version, installation commands, environment variables, indexing command, and query command. Error messages should identify likely fixes, such as installing dependencies, setting an API key, adding files to the data folder, or running indexing before querying.

Data quality also affects answer quality. Duplicated documents can dominate retrieval results. Old versions of a policy may conflict with newer ones. Tables may lose their relationships when converted to plain text. If two sources disagree, a simple RAG application may not know which is authoritative. These are limitations to document and, where possible, address through careful source selection and metadata. A transparent pipeline makes these issues easier to discover because the user can inspect the source passages behind each response.
